# 0004. Bank details encrypted at rest; last 4 digits only in the API

Status: accepted 2026-11-10
Context: employees' routing and account numbers are sensitive financial data. The repo is public and the data is simulated, but the skill's aim is production habits. A database dump, backup or SQL log shouldn't expose account numbers.
Options:
1. **Application-level AES-256-GCM** (Python `cryptography`, AESGCM).
   - Keys `PAYROLL_FIELD_KEYS` (JSON `{kid: base64 32-byte key}`) and `PAYROLL_FIELD_ACTIVE_KID`. The kid is stored as a prefix of each ciphertext, so old values stay decryptable after rotation.
   - Both routing and account numbers are encrypted.
   - The plaintext `account_last4` is stored separately for display.
   - Full numbers are decrypted in two places only: at approval and retry, to copy them into the attempt's encrypted bank snapshot (re-encrypted with the active key), and for `/v1/internal/payouts/{id}/instruction`, which reads that snapshot. No user-facing API decrypts them.
2. **pgcrypto in the database.** The key would travel in SQL statements and could end up in logs.
3. **Plaintext, masked in the API.** Simple, but a dump exposes everything.
4. **Tokenize at the processor** (store only a bank token). The right long-term answer with a real provider, but bank-stub would need a vault.
Recommendation: option 1 now, and move to option 4 when a real provider is chosen.
Decision: the recommendation above, accepted by the user on 2026-11-10 (plan sign-off).
Consequences:
- One more secret, generated by `dev-env.sh`.
- The startup check refuses a missing key or a `dev-` key in uat/prod.
- Payout attempts store an encrypted bank snapshot. It's nulled by the same purge that removes a deactivated employee's details after 30 days.
- Unit tests cover the encrypt/decrypt round trip, rejection of a tampered ciphertext, and the API never returning the full number (including Schemathesis responses).
